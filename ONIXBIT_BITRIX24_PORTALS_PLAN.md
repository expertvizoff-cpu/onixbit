## Решение

Для работы с двумя порталами Битрикс24 используем более правильный и долгосрочный вариант подключения:

- OAuth / локальное приложение / приложение с нужными scopes как основной путь;
- входящие вебхуки только как временный быстрый вариант для ограниченных задач или первичного read-only аудита;
- официальный Bitrix24 MCP используем для актуальной REST-документации, а не как доступ к порталам;
- реальные изменения в порталах выполняются только через авторизованный доступ к конкретному порталу и после явного выбора target.

Официальные источники:

- REST API: https://apidocs.bitrix24.com/api-reference/
- MCP для REST-документации: https://apidocs.bitrix24.com/ai-tools/mcp.html

Предыдущее правило остается полезным как контекст: отдельный проект не был технически обязателен, но выбран как более чистый вариант, чтобы не смешивать сайт Onixbit и Bitrix24-операции.

В новом проекте нужно соблюдать жесткое разделение контекстов:

- `cloud` - облачный портал Битрикс24;
- `box` - коробочный портал Битрикс24.

Дополнительный репозиторий или отдельная рабочая копия коробочного кода внутри или рядом с `onixbit-b24` понадобится позже, если:

- для коробки будет выгружаться большой объем PHP-кода, шаблонов, модулей или `/local`;
- изменения в коробочной версии станут отдельным полноценным проектом разработки;
- понадобится независимый Git-цикл, staging, релизы и rollback именно для коробки.

Текущий оптимальный вариант: в `onixbit-b24` хранить документацию, безопасные скрипты, схемы аудита и шаблоны конфигурации без секретов. Реальные секреты держать только в локальных ignored-файлах или в защищенном хранилище.

## Имена контекстов

Все будущие команды, скрипты и документы должны явно указывать портал:

- `target: cloud`
- `target: box`

Запрещено выполнять команду, если target не указан явно.

Рекомендуемые локальные файлы секретов, которые не коммитятся:

- `.env.bitrix24.cloud.local`
- `.env.bitrix24.box.local`

Они попадают под текущее правило `.gitignore`: `.env*`.

## Минимальная структура переменных

Шаблон имен, без реальных значений:

```bash
# .env.bitrix24.cloud.local
BITRIX24_TARGET=cloud
BITRIX24_PORTAL_HOST=
BITRIX24_AUTH_MODE=oauth
BITRIX24_CLIENT_ID=
BITRIX24_CLIENT_SECRET=
BITRIX24_REFRESH_TOKEN=
BITRIX24_WEBHOOK_URL=
```

```bash
# .env.bitrix24.box.local
BITRIX24_TARGET=box
BITRIX24_PORTAL_HOST=
BITRIX24_AUTH_MODE=oauth
BITRIX24_CLIENT_ID=
BITRIX24_CLIENT_SECRET=
BITRIX24_REFRESH_TOKEN=
BITRIX24_WEBHOOK_URL=
BITRIX24_BOX_SSH_HOST=
BITRIX24_BOX_SSH_USER=
BITRIX24_BOX_PROJECT_PATH=
```

Правило: реальные URL вебхуков, токены, пароли, refresh tokens, SSH-ключи, домены закрытых порталов и клиентские данные не писать в чат, документацию или код.

## Безопасный порядок работы

1. Подключить официальный Bitrix24 MCP для документации, если он доступен в текущей Codex-сессии.
2. Создать отдельного технического пользователя для каждого портала.
3. Настроить OAuth / локальное приложение с минимальными scopes под задачу.
4. Для коробки отдельно подтвердить staging/backup и границы изменения кода.
5. Выполнить read-only аудит: список доступных методов, права, CRM-структура, пользовательские поля, воронки, роботы, открытые линии, интеграции.
6. Составить план изменений отдельно для `cloud` и `box`.
7. Выполнять изменения маленькими шагами, с dry-run/read-only режимом там, где возможно.
8. Перед любым изменением, которое затрагивает данные, настройки CRM, роботов, права, вебхуки или коробочный код, получать явное подтверждение.

## Правила для коробочной версии

Для коробки REST-доступа может быть недостаточно. Дополнительно может понадобиться:

- SSH/SFTP-доступ;
- путь к проекту;
- информация о версии 1C-Битрикс / Битрикс24;
- staging или тестовая копия;
- свежий backup файлов и БД;
- понимание, где находятся доработки: `/local`, модули, шаблоны, обработчики событий, агенты, cron.

Не редактировать ядро `/bitrix`, если нет отдельной причины и согласованного rollback.

## Рабочая маркировка

Любая будущая задача должна начинаться с явного указания:

```text
Портал: cloud | box
Режим: audit | dry-run | change
Область: CRM | users | tasks | openlines | sites | automation | code | other
Риск: read-only | reversible | data-changing | production-impacting
```

Если в задаче нет этой маркировки, Codex должен сначала уточнить target и режим.

## Текущее правило

MCP не заменяет авторизацию в портале. MCP нужен для актуальной документации REST API. Для реальных действий нужен OAuth, локальное приложение, вебхук или UI/админ-доступ к конкретному порталу.
